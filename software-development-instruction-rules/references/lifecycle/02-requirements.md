## 阶段二：需求分析

进入条件：已知要研究的业务问题、主要受影响人群与初步范围；探索可与可行性分析并行，正式建立交付基线前须确认决策负责人。

必做事项：

- [REQ-01] 区分功能需求、非功能需求、业务规则和实现约束。
- [REQ-02] 为承诺交付的需求记录稳定标识、来源、优先级、验收标准和确认状态；草案标明待确认事项。
- [REQ-03] 描述正常流程、备选流程、失败情况、边界条件、权限及相关数据规则。
- [REQ-04] 将质量要求量化；用可测试标准替换“快速”“安全”“易用”等模糊表述。
- [REQ-05] 解决需求冲突，并记录未解决的假设。
- [REQ-06] 通过影响分析和审批控制需求变更。
- [REQ-07] 从访谈、观察、现有流程、数据或原型等适合的来源获取需求，并记录关键结论与待确认问题。
- [REQ-08] 区分业务目标、干系人需要与系统需求；识别重复、冲突、派生需求和项目范围之外的请求。
- [REQ-09] 对关键业务规则给出具体示例；对非功能需求写明测量条件、阈值和验证方法。
- [REQ-10] 确认需求基线及其版本；每次变更应评估设计、数据、接口、测试、工期与发布的影响。
- [REQ-11] 对需求集明确问题陈述、目标用户、范围边界和成功指标；需要分批交付时，将优先级与依赖关系对应到交付增量。
- [REQ-12] 每条重要需求应能回答“何时触发、系统如何响应、怎样验收”；需求细节尚未确认时，标明假设和决定者，不得写成已批准事实。

### 需求工程知识与实施方法

1. **计划获取**：先识别干系人及其决策权，选择访谈、观察、工作坊、现有系统分析、数据分析或原型。记录来源、时间、背景和相互冲突的观点，避免把某个人的表述当作全体用户共识。
2. **分层分析**：业务需求描述价值和业务结果；干系人需求描述角色需要；系统需求描述可验证的行为和质量；设计约束描述必须遵守的技术或制度边界。下层要求须说明如何支持上层目标。
3. **行为表达**：可使用用户故事、用例、事件响应表或流程图。用户故事应补足验收条件；复杂规则可给决策表、状态转换或计算示例。记录触发、前置条件、主流程、备选和异常流程、后置条件及权限。
4. **质量属性**：性能要求写明负载、数据规模、测量环境、分位数和阈值；可靠性说明故障条件、可用性或恢复目标；安全与隐私说明资产、主体、授权和数据生命周期；无障碍说明适用标准与测试场景。目标值应由有权干系人确认，不由技能臆定。
5. **分析与消歧**：检查完整性、一致性、必要性、可行性、无歧义、可追踪和可验证。区分未知问题与已知不做的范围，识别重复、冲突、隐藏假设以及派生需求。高风险冲突需在承诺实现前作出决定。
6. **排序与分批**：考虑价值、时限、风险、依赖、成本和法规义务。优先级不是单一“高/中/低”标签；记录排序依据和取舍，确保一个增量形成可用且可验收的业务结果。
7. **确认与基线**：由相应负责人核对需求是否表达了真实意图，保留版本、审批或确认状态。探索中的草案可以继续细化，但不可伪装成已批准的交付基线。
8. **变更管理**：每次变更说明来源、理由、差异、受影响需求、设计/接口/数据/测试、成本和发布日期，再由有权者决定纳入、延期或拒绝；同步更新基线和追踪链接。敏捷积压项也需要可见的决定记录。

### 需求门禁检查

- **完整性**：首个增量所需的业务流程、角色、数据、异常和质量条件是否足以设计与验证？未决问题是否有负责人和截止点？
- **可验收性**：每项承诺需求能否用示例或“给定条件—当发生—则应”的形式观察结果？无法直接测试的约束是否有审查或分析方法？
- **一致性**：业务规则、界面文案、接口字段和数据定义是否使用同一术语与版本？冲突如何裁决？
- **追踪性**：能否从业务目标找到需求与验收证据，也能从实现任务反查来源？无价值或无来源的需求应被质疑。
- **交接准备**：设计者是否拿到权威版本、范围与优先级、关键场景、质量目标和未决风险？

所需证据：

- 经有权干系人确认的需求或等效的版本化记录
- 重要业务流程的用例或其他行为模型
- 验收标准
- 需求追踪记录
- 需求来源、冲突处理和变更决策记录
- 需求到设计、任务与验收证据的交接链接，及尚未解决的问题
- 关键规则实例、质量属性测量条件、优先级取舍及需求基线版本

退出门禁：

- [REQ-G01] 对计划正式交付的需求，关键行为仍有歧义、缺少授权确认、不可行或无法验证时，不得将其作为已就绪的实现输入；可继续用原型和分析消除未知。
- [REQ-G02] 范围内需求若没有可判断的验收条件或所需质量目标，不能宣称需求门禁通过。未纳入当前增量的需求不必在本次门禁中全部细化。
