## 阶段七：运行与维护

进入条件：服务或交付增量已投入使用，运行责任、版本、关键用户路径和故障升级方式可定位；运维准备应在发布前完成。

必做事项：

- [OPS-01] 按适用情况监控可用性、延迟、错误、资源使用、安全事件和关键业务结果。
- [OPS-02] 记录故障时间、影响、响应、恢复和根因。
- [OPS-03] 对严重故障处理根本原因，不能仅抑制表面症状就关闭故障。
- [OPS-04] 对缺陷修复、依赖升级、配置变更和功能改进，按比例执行需求、影响、实现、验证和发布控制。
- [OPS-05] 按风险确定的频率测试备份恢复和灾难恢复。
- [OPS-06] 执行数据保留、审计、隐私、凭据轮换和访问复核要求。
- [OPS-07] 为重要服务明确可观测指标、告警责任和响应路径；根据故障与用户影响调整阈值，避免仅凭服务器存活判断业务可用。
- [OPS-08] 对重复故障、积压缺陷和持续偏离质量目标的情况设定改进事项与负责人，并跟踪其效果。
- [OPS-09] 将重大故障复盘产生的纠正措施追踪到需求或缺陷、实现、回归验证和后续发布，验证措施是否降低复发风险。
- [OPS-10] 维护在役版本、支持窗口、弃用和支持终止信息；对用户或依赖方提供相称的升级通知与迁移路径。

### 运行维护知识

- **服务水平**：根据用户可感知的关键路径选服务指标（如成功率、延迟、数据新鲜度），约定目标、统计窗口和排除规则。服务器在线率不能代替用户任务成功率；目标值应结合业务影响和成本决定。
- **可观测性**：让日志、指标和追踪能关联请求、版本、依赖和失败原因，同时保护敏感数据。告警要有行动意义，包含责任人、排查入口与升级路径；持续噪声需要调整。
- **事件处理**：按影响分级，先确认范围并遏制损害，再恢复服务、沟通状态、保留证据。应急修复可走简化路径，但事后仍需补齐审查、测试、变更记录和风险复核。
- **故障复盘**：区分直接触发因素、系统性原因和放大影响的条件。纠正措施要有负责人、验证方法和完成时间；复盘关注改进系统而非归罪个人。
- **问题与维护**：将重复故障、容量趋势、技术债、依赖寿命和安全风险纳入维护计划。变更类型可分为纠错、适应环境、改进功能与预防风险，但都应评估对现有行为和数据的影响。
- **恢复能力**：检查备份是否成功之外，还要按风险演练可恢复性，确认恢复时间与数据损失是否满足要求。检查长期保留、访问权限、密钥轮换和灾难恢复依赖。
- **持续改进**：用用户影响、缺陷逃逸、交付周期和事件趋势评估改进效果；指标只能辅助决策，不能因为数值好看就掩盖单次重大损害。
- **变更闭环**：生产缺陷形成新需求或风险项后，链接影响分析、设计/实现、回归验证、发布和运行观察。对未解决的长期风险，保持责任和重审日期。
- **产品安全响应**：安全报告、在役版本漏洞、依赖通告、补丁和支持终止按 [漏洞响应与产品支持](../engineering/vulnerability-response.md) 处理；服务恢复不能替代漏洞披露和受影响版本闭环。

### 运行与维护门禁检查

1. 关键业务路径是否可被观察，告警是否能指向可执行的响应？
2. 对重大事件，影响范围、恢复结果、根因假设和纠正措施是否可核实？
3. 维护变更是否检查回归、数据与配置影响，并对应到已发布版本？
4. 备份与恢复目标是否有实际演练证据；不达标时有何临时措施？
5. 故障或改进任务关闭后，效果如何验证，谁继续观察？

所需证据：

- 运行健康与故障记录
- 重大故障的根因分析和纠正措施记录
- 变更与回归测试历史
- 恢复测试证据
- 服务目标、告警与改进行动的跟踪记录
- 故障改进事项的关闭证据及后续责任人
- 服务指标定义、事件时间线、用户影响及纠正措施验证方式

退出门禁：

- [OPS-G01] 修复效果、回归风险、运行影响和后续责任尚未验证时，不得将重大故障或维护变更标记为已完全解决；服务恢复与根因措施关闭可以是两个不同状态。
- [OPS-G02] 当前变更若触发新的发布，应重新应用相关实现、验证和发布门禁；运行稳定不自动证明下一次变更安全。
