## 阶段四：编码实现

进入条件：受控交付任务有需求或缺陷来源、验收条件、必要的接口与数据决策；不确定的技术问题可先作为独立实验处理。

必做事项：

- [IMP-01] 对受控交付仅实现已确认的范围，并保留与原始需求或缺陷的追踪关系；探索性代码须标明其边界。
- [IMP-02] 遵循仓库在结构、命名、格式、错误处理、日志和依赖管理方面的约定。
- [IMP-03] 校验不可信输入，并在适当的信任边界执行授权检查。
- [IMP-04] 不得硬编码或提交密码、令牌、密钥及环境专用机密。
- [IMP-05] 为会修改状态的操作明确事务边界和部分失败时的处理方式。
- [IMP-06] 随实现新增或更新有针对性的自动化测试。
- [IMP-07] 对依赖、构建和数据库迁移使用可识别版本；迁移脚本与对应代码一并审查和验证。
- [IMP-08] 将关键设计不变量落实为代码约束、数据约束或测试；不能只依赖注释或图示维持正确性。
- [IMP-09] 除非确有必要、已说明并经过评审，否则不要夹带无关重构。
- [IMP-10] 合并到受保护的集成或发布分支前，必须完成代码审查。

### 实现知识与工作分解

- **任务切片**：把已就绪需求拆成可检查的实现任务，列出接口、数据、前端、验证与迁移依赖。每个任务应能指向需求或缺陷及其验收条件；跨组件修改先约定契约和集成顺序。
- **实现顺序**：优先消除高风险不确定性，再完成最小可用的端到端路径，逐步补足异常和边界行为。实验性代码若要进入正式交付，须满足相同审查与验证要求。
- **代码结构**：将业务规则放在可定位、可测试的位置；保持接口职责清晰，避免重复、隐式全局状态和难以控制的副作用。遵循现有项目约定，不为抽象而抽象。
- **输入与权限**：在服务端或可信边界校验类型、长度、格式和业务约束；对资源级操作执行授权。日志和错误信息不得泄露敏感数据，错误处理应让调用者知道能否重试。
- **状态与数据**：事务边界与设计一致。并发写入、重复请求、异步消费和部分失败应有确定行为；数据库约束或幂等键可用于落实业务不变量，不能只依赖界面防错。
- **依赖与供应链**：使用受控版本和来源，检查许可证、已知风险与升级影响；构建应可复现到可识别修订。机密经适当存储和注入，不进入代码、测试快照或日志。公共制品、高风险构建或 CI/CD 变更还须读取 [安全设计与软件供应链](../engineering/security-supply-chain.md)。
- **迁移与兼容**：数据模式和 API 变化须考虑滚动部署期间的新旧版本共存；优先设计可渐进切换和验证的步骤。破坏性迁移应有备份、恢复或前向修复决定。
- **代码审查**：审查者要检查需求对应、关键算法和规则、异常路径、安全边界、测试质量、可维护性及迁移影响。对意见和剩余风险留有处理结论；“已看过”不足以证明高风险问题已解决。
- **完成定义**：代码合并只是实现环节的一个状态。交付项还需与适用的验证、文档、运行和发布准备一致；查看 [全流程控制与判定](../governance/controls.md) 中的工作就绪与完成定义。

### 实现门禁检查

1. 变更是否确实覆盖了目标需求或缺陷，且没有未授权的行为或范围扩张？
2. 设计中关键不变量、错误处理、权限和数据一致性是否落实为代码或可执行约束？
3. 构建、相关自动检查与人工审查是否针对同一修订，失败项是否解决？
4. 新增依赖、配置、迁移、日志和文档变化是否与代码一起交付并可追踪？
5. 对无法通过常规测试证明的高风险行为，是否已有其他验证计划与负责人？

所需证据：

- 可追踪的源码变更
- 通过的构建、格式检查、静态检查和相关单元测试
- 代码审查结论
- 行为或契约变化时更新的技术文档
- 与实现相匹配的迁移、配置和依赖变更记录
- 需求/缺陷到变更与测试的链接、审查意见处置及构建修订标识

退出门禁：

- [IMP-G01] 对受保护的集成或发布分支，必要检查失败、缺少所要求的审查、存在已知泄露的机密，或关键行为变更缺乏验证时，不得合并代码。
- [IMP-G02] 不得仅为让失败的变更通过而删除、跳过、弱化有效测试，或改写正确的预期结果。
- [IMP-G03] 实现门禁通过不等于验收或发布通过；将已知限制、未测场景和后续验证责任交给下一阶段。
