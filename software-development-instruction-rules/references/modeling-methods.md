# 建模方法与一致性检查

仅在模型选择、制作或设计评审需要时读取。模型用来回答具体问题；选最少的视图覆盖关键不确定性。图的源文件、文字规范和代码契约都可以是可维护的模型表达。

## 按问题选择视图

| 需要回答的问题 | 可选模型 | 重点检查 |
| --- | --- | --- |
| 谁与系统交互、边界在哪里 | 系统上下文、用例 | 参与者、外部系统、职责边界、范围内外 |
| 业务步骤、分支和责任如何流转 | 活动、BPMN、流程图 | 触发、正常/异常路径、终止、责任交接 |
| 概念与规则是什么 | 领域模型、类图 | 名称、关系、基数、不变量；不要过早加入数据库实现细节 |
| 状态何时改变 | 状态机 | 状态、事件、守卫条件、非法转移、并发 |
| 多组件如何协作 | 顺序图、接口契约 | 调用、异步消息、超时、失败、重试、幂等性 |
| 数据如何存储和流动 | 数据模型、数据流 | 所有者、键、约束、敏感数据、迁移与保留 |
| 系统如何部署与隔离 | 部署/组件视图 | 运行节点、网络/信任边界、故障域、可观测性 |

## 构建与检查

1. 写明模型的问题、范围、版本和读者；先核对权威需求及术语。业务模型应描述业务事实，设计模型再表达技术分工。
2. 对关键场景同时检查正常、备选、拒绝、超时、重复、恢复和边界条件。图无法清楚表达的规则写在紧邻图的文字契约中。
3. 跨视图核对同一实体、状态、接口、事件和数据定义；例如状态图允许的转移必须与接口错误码、权限规则和测试用例一致。
4. 将关键元素关联到需求、设计决策与验证案例。变更后更新受影响视图并重新检查一致性；不要求所有图都包含全量追踪标记。
5. 评审可用文字加可编辑图，也可用受版本管理的代码定义或图源文件。选择 draw.io 等工具时保留可编辑源；导出的图片单独不能承载需要维护的完整规则。

## 常见建模错误

- 用数据库表结构冒充领域规则，导致业务词汇、约束和例外未被表达。
- 只有成功路径；异常、并发、重试和补偿被留给实现者猜测。
- 同一字段、状态或接口在不同图和 API 文档中含义不一致。
- 为每个需求强制画全套 UML 图，导致图过期而无人使用。只保留能支持设计、沟通或验证的视图。

模型门禁看其是否足以支持关键设计和验证，不按图的数量判定。对高风险但尚无证据的行为，记录待验证假设和负责人。
