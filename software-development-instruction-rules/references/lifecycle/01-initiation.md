## 阶段一：立项与可行性分析

进入条件：存在待解决的问题、机会或外部义务，并能找到提出者；此时目标和范围可以仍是待验证假设。

必做事项：

- [INI-01] 明确业务目标、目标用户、系统边界、成功指标、负责人和主要干系人。
- [INI-02] 按适用情况评估技术、经济、操作、进度、法律、安全、隐私及合规可行性。
- [INI-03] 识别主要假设、依赖、约束和高影响风险。
- [INI-04] 对不确定或高风险的技术判断，先通过有针对性的概念验证，再决定是否全面实施。
- [INI-05] 选定适合范围稳定性、风险和交付频率的过程方式，并定义决策、评审、沟通与变更机制。
- [INI-06] 为预期收益设定可测量的成功指标，并检查关键资源与外部协作是否可获得。
- [INI-07] 将近期范围分解为可验收的交付项，标明先后依赖、估算依据与不确定性；关键路径或固定期限存在时，明确其影响和调整空间。

### 核心知识与实施方法

- **立项依据**：说明当前问题、现状基线、预期收益和不做项目的后果。区分“业务成果”（如处理时间降低）与“交付物”（如上线一个服务），为收益指定测量口径、测量时点和责任人。
- **方案与可行性**：至少考虑维持现状、改进既有系统、采购或新建中适用的选项。比较价值、总拥有成本、技术与数据约束、组织采纳难度、交付时间及不可逆风险；无需为显然不适用的方案编造完整商业案例。
- **采购方案**：涉及 SaaS、商业组件、外包或关键开源能力时，读取 [采购与供应商控制](../governance/acquisition-and-suppliers.md)，把支持、数据、连续性和退出成本纳入可行性，而不只比较采购价格。
- **干系人与治理**：识别受影响用户、业务负责人、交付团队、运维、数据或安全责任人及外部依赖方。明确谁提供需求、谁决定优先级、谁验收成果、谁接受剩余风险；不同角色可由同一人承担。
- **范围边界**：列出首期目标、明确排除项、接口与数据边界、重要假设和约束。将探索性工作与承诺交付分开记录，防止原型结果被误当生产可行性证明。
- **交付策略**：根据需求变化、风险、反馈速度和合规义务选择迭代、增量或阶段式安排。定义每个增量的价值、验收条件和对既有服务的影响；生命周期门禁随增量重复应用。
- **工作与估算**：先识别成果和依赖，再估算工作量与历时。验证、集成、迁移、培训及切换属于工作范围。输入不足时给区间和验证计划；需深入估算时读取 [计划与估算方法](../governance/planning-estimation.md)。
- **风险验证**：对高影响假设写明“如果假设错误会发生什么”、验证方式、最迟决策时间和负责人。概念验证应测量特定不确定性，例如吞吐量、第三方接口能力或数据质量。

### 立项门禁检查

1. 问题、目标用户和收益指标是否可描述，范围内外是否被主要干系人理解？
2. 关键方案为什么可行，技术、数据、资金、能力和合规限制是否已有证据或验证安排？
3. 对不可逆或高影响的决策，是否有备选方案、触发条件和真实决策负责人？
4. 初步计划是否包含关键依赖、容量、估算依据与不确定性？承诺日期是否与可用证据相称？
5. 下一步是需求探索、原型验证还是正式范围承诺？分别需要哪些已确认输入？

所需证据：

- 项目目标和范围说明
- 可行性结论
- 初步风险与依赖清单
- 明确的决策负责人
- 初步交付计划、关键依赖与成功指标
- 估算假设及对高风险依赖的验证或应对安排
- 方案比较、主要假设的验证结果或待验证安排，以及首个增量的验收边界

退出门禁：

- [INI-G01] 问题、范围、决策责任或高影响可行性风险未澄清时，不得把交付范围、日期和预算宣布为已获证实的正式承诺；可以继续开展用于澄清问题的需求探索和概念验证。
- [INI-G02] 正式进入受控交付前，须明确初始范围与成功标准、决策责任、关键风险处理及下一阶段需验证的假设。项目制度要求批准时，核实真实批准状态。
