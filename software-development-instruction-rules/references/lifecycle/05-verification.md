## 阶段五：验证与确认

进入条件：可识别被评估的需求范围、候选构建及环境；测试设计可在实现前开始，正式门禁判定针对实际候选版本。

必做事项：

- [VER-01] 将需求和风险映射到测试用例或其他验证方法。
- [VER-02] 按适用情况覆盖正常、备选、边界、错误、权限、并发和恢复场景。
- [VER-03] 在适当边界开展单元、集成、系统和验收测试。
- [VER-04] 验证适用的性能、安全、兼容性、无障碍、可靠性、迁移和恢复要求。
- [VER-05] 记录每个缺陷的严重程度、可复现证据、影响、处理结论和目标版本。
- [VER-06] 对可重复测试的已修复缺陷增加回归测试。
- [VER-07] 确保被测构建、配置、环境和数据可识别。
- [VER-08] 在测试前明确测试范围、环境、数据、进入条件及退出标准；将高风险路径安排在足够早的阶段验证。
- [VER-09] 对无法自动化的验收、可用性或恢复验证，保留可复核的步骤、结果和执行者记录。
- [VER-10] 区分“测试未执行”“测试失败”“不适用”和“已通过”；任何缺口均须说明影响与处理决定。
- [VER-11] 检查结果是否对应当前候选发布版本；测试报告应保留实际结果、环境和缺陷链接，而非只给出通过百分比。
- [VER-12] 不稳定测试、重试通过、跳过或隔离测试必须可见，并记录影响、负责人、修复期限和是否影响门禁；不得把未执行或被重试掩盖的失败计为稳定通过。
- [VER-13] 对高影响业务规则和安全控制，按风险使用负向测试、故障注入、变异测试或等效方法证明验证能够发现错误；不要求所有项目统一采用某一种工具。

### 验证与确认知识

- **验证和确认**：验证检查产品是否符合已约定需求与设计；确认检查交付结果是否解决了真实用户问题。技术测试通过不能替代业务验收，业务演示也不能替代适用的安全和可靠性验证。
- **风险驱动策略**：按业务损失、故障概率和变更影响决定测试深度。优先测试资金、隐私、权限、不可恢复数据和高流量路径；低风险纯展示变更可缩减范围，但要说明原因。
- **层级与边界**：单元测试覆盖局部规则，组件或契约测试覆盖模块约定，集成测试覆盖真实接口与数据交互，系统测试覆盖端到端行为，验收由有权业务方依据业务标准作出。各层作用不同，不用一个大型端到端套件代替全部检查。
- **测试设计技术**：按输入等价类和边界值找极端输入；用决策表检查组合业务规则；用状态转换检查合法与非法路径；用场景测试覆盖正常、备选、失败和恢复流程。对并发与时间条件设计可复现的控制方法。
- **非功能验证**：性能测试需给出负载、数据规模、环境与阈值；安全验证关注威胁和信任边界；可用性与无障碍要基于用户任务；备份恢复需要实际演练。工具扫描只能提供部分证据，不能代替风险判断。
- **测试环境与数据**：记录构建、配置、依赖、迁移、特性开关、环境差异与数据集。生产敏感数据用于测试时须遵守授权和保护要求；数据伪造应保留关键业务分布和异常特征。
- **缺陷闭环**：记录复现步骤、期望与实际、严重程度、影响范围、定位修复版本和回归结果。重复出现或影响多个需求的缺陷应检查共同原因；延期修复需有风险接受与目标时间。
- **覆盖解释**：报告已验证需求、未测需求、失败项及其影响。覆盖率、通过率和扫描数量只是辅助指标，无法单独证明业务风险已被控制。
- **测试可信度**：关注测试是否执行了目标变更、断言是否能失败、结果是否可重复。重试只能用于诊断瞬时问题，不能把未知不稳定性改写为通过。

### 验证门禁检查

1. 当前候选版本的每项承诺需求是否有通过证据或已说明的替代验证方式？
2. 高影响质量属性和故障场景是否在有代表性的条件下得到验证？
3. 缺陷是否按严重程度和业务影响处置，修复后是否做相关回归？
4. 未执行或不适用的测试是否明确区分，未测风险是否被有权人员接受？
5. 业务验收的决策者、标准、实际结果及版本是否可追溯？

所需证据：

- 与需求和风险关联的测试结果
- 缺陷状态与已接受的剩余风险
- 回归验证证据
- 适当负责人作出的验收决定
- 未测范围及其风险处置记录
- 候选发布版本与验收结论之间的关联
- 测试策略与设计依据、环境和数据条件、失败项及未测风险清单

退出门禁：

- [VER-G01] 对拟发布范围，验收标准未满足、必要覆盖缺失，或未解决缺陷超过已确定的发布风险阈值时，不得判定验证门禁通过或批准发布。
- [VER-G02] 不得仅通过修改预期结果将失败改成通过。
- [VER-G03] 不得用旧构建的测试结论覆盖未经评估的新变更；若只做增量回归，要记录影响分析和回归范围依据。
- [VER-G04] 关键测试持续不稳定、未实际执行目标代码或无法证明有效断言时，不得以表面通过结果放行对应高风险行为。
