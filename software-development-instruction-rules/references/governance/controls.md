# 全流程控制与门禁判定

## 工作方法

1. 明确当前生命周期阶段、拟进入的下一阶段以及本次交付增量。
2. 识别风险信号并按需读取 [风险配置与适用性](risk-profiles.md)，确定适用控制和明确不适用项。
3. 确定评审范围及项目已有的权威材料；优先查看实际工单、设计、源码、测试、发布和运行记录。
4. 同时应用通用约束、当前阶段退出门禁及适用的专项控制，按控制编号逐项关联可复核证据。
5. 区分已核实的事实、项目方声明、未解决的风险、缺失证据和无法检查的内容。
6. 阻断性要求未满足时，不得宣布阶段完成；证据无法取得时，不推断为已通过或已失败。
7. 对未通过或未评估的事项，指出缺失的材料或决策、责任归属和继续推进所需的最小行动。

维护类小改动可按风险缩减交付材料，但必须保留完整链路：需求或缺陷 → 影响分析 → 设计决策 → 实现 → 验证 → 发布或回滚记录。若工单、拉取请求、测试或纳入版本管理的项目文件已清楚记录相关证据，无需另造形式化文档。

八个阶段是检查软件全生命周期的逻辑视角，不要求项目采用瀑布式顺序。增量、迭代、敏捷和持续交付项目，应按每个可交付增量及其风险应用相应门禁；探索性原型可以先验证假设，但若要进入正式交付，仍须补齐相关需求、设计、验证和发布证据。不要因为某阶段在流程图上尚未出现，就推迟该阶段已可识别的风险。

## 阶段交接契约

交接给下一阶段或负责人时，明确当前交付增量的输入依据、已完成的输出、验证或评审结论、版本或链接、未决假设与风险、下一步责任人。下一阶段接收者应能据此定位权威材料和继续工作；材料可存在于已有工单、拉取请求或项目文档中，无需固定模板。交接前检查需求、模型、接口、数据规则和测试是否指向同一版本，发现不一致时记录差异及处理决定。

### 工作就绪与完成的区别

- 工作就绪（Definition of Ready）回答“是否有足够信息开始本次工作”：目标和范围、接收标准、关键依赖与未决问题可见。未澄清的高风险问题应先探查，不应伪装成已确定需求。
- 完成定义（Definition of Done）回答“这次交付是否真的完成”：适用的代码与文档更新、验证结果、质量与安全证据、运行准备和交接均与同一交付版本对应。按变更风险选取维度，不给所有工单套同一清单。
- 阶段退出门禁回答“是否可以承担下一阶段的风险”。一项工作可已编码完成却仍未达到发布门禁；原型可完成探索任务却仍不能作为正式交付。分别报告状态，避免相互替代。

### 证据质量

- 优先采用可复查的一手记录：版本化需求或工单、设计决策、源码和构建标识、测试运行、缺陷记录、部署日志、监控数据。口头声明可列为待核实信息。
- 每项关键证据要能定位到交付增量和版本，说明执行条件、实际结果及结论；过期版本的通过结果不能自动证明当前版本通过。
- 抽样审查时说明样本、覆盖范围和未覆盖部分；不要把样本结论推广到全部需求或全部系统。
- 组织已有权限、签核或合规要求应沿用；本技能不创造新的审批角色。需要风险接受时记录具有相应职责的真实决策者和决定。
- 持续审查、跨版本比较、例外管理或机器处理时，按 [控制编号与证据记录](evidence-and-control-ids.md) 记录控制、范围、状态、证据、版本、实际结果、负责人和时效。

## 门禁判定

- PASS：适用的阻断性条件均有可复核证据支持；不存在未经处置的重大风险。
- CONDITIONAL：阻断性条件已满足；仅剩明确不阻断的事项，且有负责人、处理期限和被接受的影响。不得用它放行尚未满足的强制要求。
- BLOCKED：已检查的权威材料表明强制条件未满足，或应存在的必需交付证据确实缺失；指出具体条款、影响与解除阻断的行动。
- NOT_ASSESSED：尚未取得足够的项目材料、未检查实际交付物，或用户仅要求拟定规范；列出需要检查什么，不推断项目通过或阻断。

门禁结论是对所检查范围的判断，不自动代表项目负责人批准继续实施、合并、发布或停用系统。若组织另有审批制度，报告其状态；不能把技能自己的检查当成真实审批。

### 门禁适用性与风险裁剪

1. 先界定“本次交付增量是什么、要进入哪一阶段、哪些系统和用户受影响”。未纳入本次增量的未来需求不应阻断当前增量；共享基础设施和数据迁移的影响不能因范围写得小而遗漏。
2. 将条件分成通用不变量、与本次风险相关的阶段条件、组织或合同另有要求的条件。对不适用项说明原因；对适用项列出证据、版本和负责人。
3. 判定阻断时指出实际未满足的条件及后果。若证据缺失且项目确应产生该证据，判为 BLOCKED；若尚未取得材料或尚未开始评审，判为 NOT_ASSESSED。
4. 只有非阻断遗留事项可进入 CONDITIONAL。若团队希望改变强制条件，应由有权者先按项目治理规则正式修订门禁或范围，再重新评估，不能由审查者临时改写通过标准。
5. 同一增量的门禁可能分层通过：实现 PASS、验证 BLOCKED、发布 NOT_ASSESSED。逐层说明，不用一个总状态掩盖下游风险。
6. 风险配置只决定检查深度，不证明任何控制已经满足；配置叠加时应用控制并集，项目已有更严格规则时沿用项目规则。

例如，纯文案修改通常不需要新架构图、数据迁移预演或性能压测，但仍需追踪修改来源、验证显示效果并识别发布版本。改变用户权限或迁移交易数据的改动，则须检查授权规则、数据一致性、回归和恢复路径；“代码量少”不是减免理由。

## 通用约束

- [GEN-01] 每项进入受控交付的实现变更都必须可追溯到已确认的需求、缺陷、风险处置或维护任务；探索性实验须标明实验目的和不进入交付的边界。
- [GEN-02] 每项承诺交付的系统需求都必须有客观的验收标准和预定验证方法；交付时必须能关联实际验证证据。业务目标的成效指标可在交付后持续衡量。
- [GEN-03] 每项重大变更都必须记录原因、范围、受影响组件、风险和真实审批状态。
- [GEN-04] 在适用时，安全、隐私、可靠性、性能、无障碍和合规要求必须纳入前期工作，不得默认推迟到测试阶段。
- [GEN-05] 生成物、源码版本、构建、配置、迁移、测试结果和发布版本必须可识别。
- [GEN-06] 必须以证据为依据。不能因为某项审查、测试、审批、备份、迁移、回滚或监控措施“理应存在”，就认定它已完成。
- [GEN-07] 门禁失败即阻断推进。应直接报告失败，不能弱化门禁或暗中修改预期结果。

## 贯穿全流程的控制

### 项目治理与计划

- [GOV-01] 为范围、优先级、技术方案、验收、发布和剩余风险指定有权决策者；同一事项存在多个意见时，记录最终决策与依据。
- [GOV-02] 将目标拆成可验收的交付增量，记录任务依赖、估算依据、人员容量、预算或时间约束及计划中的不确定性；不得把未评估的日期承诺当作可行性证据。
- [GOV-03] 维护风险、问题、假设和外部依赖的负责人、影响、触发信号与应对行动；重大风险应尽早验证或升级处理。
- [GOV-04] 定期依据已完成的可验证交付物、质量结果及剩余工作更新预测；范围、日期或资源发生实质变化时，向相关决策者呈现取舍并记录决定。
- [GOV-05] 估算方法应与数据和不确定性相称：可用工作分解、历史吞吐量或区间估算；三点估算和模拟只在输入假设足够明确时采用。记录估算范围、依据、关键依赖和置信度，不得伪造精确工期。

### 需求、设计与验证追踪

- [TRC-01] 维持业务目标 → 需求或缺陷 → 设计决策与模型 → 实现 → 测试或其他验证 → 发布记录的双向追踪。小改动可用工单和拉取请求链接承载，不要求单独的矩阵文件。
- [TRC-02] 需求、设计、接口、数据规则和测试之间发生冲突时，先确认权威版本并处理冲突；不得让代码行为成为未经确认的隐性需求。
- [TRC-03] 变更评估必须识别实际受影响的正常、异常、边界、权限、并发及恢复场景，并同步更新相关模型、契约、测试和操作说明；不适用的场景无需凭空补造。
- [TRC-04] 每次门禁评审前检查权威材料链接、控制编号和版本关系是否漂移；发现失效链接、重复编号、版本错配或上下游矛盾时，记录差异、权威来源、决定和负责人。

### 配置、质量与安全

- [QSC-01] 明确配置项及其版本关系，至少能够识别需求基线、设计决策、源码、依赖、构建、环境配置、数据库迁移、测试证据和发布版本。
- [QSC-02] 对适用的质量属性定义测量条件、目标和验证方法；没有约定负载、数据规模或测量口径的“快速”“稳定”“安全”不能作为通过证据。
- [QSC-03] 对外部输入、敏感数据、凭据、第三方依赖和信任边界进行相称的安全与隐私评估；高影响风险应在设计和实现时处置，并在验证和运行中复查。
- [QSC-04] 例外及剩余风险必须记录唯一编号、涉及控制、范围、原因、影响、补偿措施、责任人、有权批准者、批准状态、到期时间、复查触发条件和关闭证据；不允许用未署名或无期限的“暂时接受”代替门禁结论。

## 常见误用

- 不用勾选了清单代替查看实际产物；自动检查结果须与被测版本对应。
- 不因项目采用敏捷或持续交付而省略风险控制，也不强制为每个小改动重走整套项目立项流程。
- 不强制使用某一种图、文档目录、工具、估算公式、覆盖率百分比或发布策略；先判断它解决的具体风险。
- 不虚构访谈、签字、测试、运行数据或通过结论；缺少证据时标明未评估或阻断原因。
- 不把源项目中的 Agent 编排、安装脚本、钩子或固定角色结构搬入本技能；本技能只定义生命周期约束和证据判定。

## 输出格式

制定或评审生命周期控制时，报告：

1. 当前阶段及拟进入的下一阶段
2. 门禁结论：通过（PASS）、有条件通过（CONDITIONAL）、阻断（BLOCKED）或未评估（NOT_ASSESSED）
3. 已核实的证据
4. 缺失或不足的证据
5. 继续推进前必须采取的行动
6. 已接受的剩余风险及批准负责人（如有）
7. 适用范围、交付增量和需要同步更新的下游材料
8. 交接给下一阶段的输入、输出、未决风险和责任人（适用时）

对正式审查，至少在发现项中给出控制编号、适用范围、状态、证据或缺失证据、对应版本、实际结果、负责人和期限。需要重复审查或机器处理时使用 [控制编号与证据记录](evidence-and-control-ids.md) 的完整字段；一次性低风险评审可以合并字段，不能省略关键事实。

按上文“门禁判定”使用状态。制定规范或缺少项目证据时，使用 NOT_ASSESSED，或在无需报告门禁结果的概念解释中省略状态。英文报告将以上项目与状态译成英文，并保持判定标准不变。
